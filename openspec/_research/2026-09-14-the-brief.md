# The brief, as published

> The take-home is not sent privately. It is printed in the job posting itself,
> under "How we hire". Read on 2026-09-14 at the Ashby listing, and re-read the
> same day at `railway.com/careers/full-stack`, which carries the identical text
> for the same single role. Where this document quotes, both pages agree.

## What was asked

`[observed]` Quoted from the posting for
*Senior Full-Stack Engineer - Product* (`jobs.ashbyhq.com/railway/6ddcfe47`):

> Build an application to spin up and spin down a container using our GQL API.
> Please deploy on Railway before the interview and we will review the code during
> your interview. The app needs to have a UI component and not just a backend that
> uses the API.
>
> You will submit your solution before the interview, and sit down with a member of
> the team and go over the above.
>
> You can, and SHOULD! ask us questions ahead of time.

## What the brief actually constrains

`[observed]` Four requirements, and they are all short:

1. Spin a container **up**.
2. Spin a container **down**.
3. Through **their GraphQL API**.
4. With a **UI component** — explicitly not a backend that merely calls the API.
5. **Deployed on Railway** before the interview.

`[inferred]` The fifth is not only a delivery instruction. Deploying on Railway
means the candidate has used the product, which is the thing a take-home for a
developer-tools company can test that a coding exercise cannot.

## What the review will be

`[observed]` The posting publishes the interview structure in minutes:

| Minutes | What happens |
|---|---|
| 0–5 | Introductions |
| 5–35 | Walking through the code, and **how you would extend it** |
| 35–50 | Technology, frameworks, how you think about product |
| 50–60 | Your questions |

`[observed]` The technical interview is stage 2 of six. Stage 3 is a *Team
Review Session*: *review the solution with two team members, focusing on
problem-solving and communication*. The code is therefore looked at twice, by
different people, and the second time the subject is how it was arrived at.

`[inferred]` Thirty of the sixty minutes are spent on the code and its extension.
That weights the work toward decisions that are legible and defensible rather than
toward feature count — a small application whose boundaries are deliberate reads
better here than a larger one whose boundaries are accidental.

`[inferred]` "How you would extend it" is a question about what was deliberately
left out. Leaving things out and saying why is therefore part of the deliverable,
not a shortfall in it.

## Requirement register

What the employer asked for, separated from what this repository assumes on top.
Tasks and acceptance criteria cite these IDs.

### Required — `[observed]`, quoted from the posting

| ID | Requirement | Words in the posting |
|---|---|---|
| R-1 | Spin a container **up** | *"spin up … a container"* |
| R-2 | Spin a container **down** | *"spin down a container"* |
| R-3 | Through Railway's **GraphQL API** | *"using our GQL API"* |
| R-4 | A **UI component**, not only a backend | *"needs to have a UI component and not just a backend that uses the API"* |
| R-5 | **Deployed on Railway** before the interview | *"Please deploy on Railway before the interview"* |
| R-6 | Code is **reviewed live**, and its **extension** is discussed | *"we will review the code during your interview"*; *"how you would extend it"* |
| R-7 | Questions are expected **ahead of time** | *"You can, and SHOULD! ask us questions ahead of time."* |

### Assumed — `[inferred]`, ours, revisable

| ID | Assumption | Why |
|---|---|---|
| A-1 | "Container" means one pre-configured service in one environment, not a picker over many | Smallest thing that satisfies R-1/R-2; the picker is the extension answer for R-6 (`D-API-6`) |
| A-2 | The token stays on a server the console owns | Public repo + public demo (`D-SEC-1`); also forced by CORS |
| A-3 | The UI must show the *real* state, including transitions | R-4 is only meaningful if the UI tells the truth about R-1/R-2 (`D-UI-1`) |
| A-4 | The reviewer will open the deployed URL without any setup | R-5 says "deploy", not "send us a token" — pending `Q-SEC-2` |
| A-5 | Which API verb "down" maps to is a product decision, not a technicality | The candidates differ in what survives (`Q-API-2`) |

### Not required — deliberately absent

Authentication on the console itself, multiple containers, logs, metrics,
volumes, custom domains, environment variables editing, a project browser.
Each is a plausible "how would you extend it" answer and is listed as such in
the change's proposal, not built.

## The open invitation

`[observed]` "You can, and SHOULD! ask us questions ahead of time." — capitalised
in the original. And, on the interview: *"The interview goes both ways. Once
again, please ask us things. Many things! Hard things."*

`[inferred]` This is an instruction, not a courtesy. Not asking anything is itself
an answer to the question they are asking about how someone works.
