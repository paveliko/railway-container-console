# Decisions

> **Schema:** `| ID | Status | Statement |`
>
> **Prefix by capability:** `D-API-N`, `D-UI-N`, `D-SEC-N`, `D-OPS-N`.
>
> **Statuses.** `ratified` — signed off. `proposed` — follows from research but not
> yet signed. `superseded` — replaced by a successor.
>
> **Mutation rule.** A ratified decision is not edited. It is superseded by a new
> `D-<CAP>-N` that references it. An agent does not move `proposed` to `ratified`.
>
> Every decision records the alternatives that were rejected. A decision without
> them is a note, not a decision.

## Railway API — `D-API-N`

| ID | Status | Statement |
|---|---|---|
| D-API-1 | **superseded by `D-API-7`** | ~~Live state comes from `subscription deployment(id)` over `graphql-transport-ws` at `wss://backboard.railway.com/graphql/v2`. The console server holds one socket, multiplexes subscriptions on it, and fans the derived state out to the browser over SSE. The steady state makes zero HTTP requests to Railway.<br><br>**Rejected:** polling `deployment(id)`. At 1 Hz that is 3 600 requests/hour against an observed budget of 1 000; at any slower cadence "starting" becomes a guess about what happened between samples, which `D-UI-1` forbids. **Rejected:** the browser opening the socket itself. CORS is pinned to `railway.com`, and the credential travels in the `connection_init` payload, so it would be in the client. **Rejected:** long-polling the console's own server — SSE with worse semantics and no reconnect story. Resolves `Q-API-3`, `Q-UI-1`. Carries a `[to-verify]`: `Q-API-7` (supported surface? counted against the budget? project tokens?). Source: `_research/2026-09-14-railway-graphql-surface.md` §1.~~<br><br>**Why it fell, 2026-09-14:** the `Q-API-6` experiment showed two things the schema could not. (1) A **project token cannot subscribe at all** — the same subscription that an account token accepts is refused for a project token, inside a `next` frame, with `"Problem processing request"`. (2) The subscription fires on changes to the deployment's **`status`**, and `deploymentStop` does not change `status` — so the one transition the console exists to show is the one the stream does not carry. Observed in `_research/2026-09-14-experiment-stop-and-start.md`. |
| D-API-2 | proposed | The credential is a discriminated union `{ kind: 'account' \| 'workspace' \| 'oauth' \| 'project', token }`. The HTTP header is a function of `kind` — `Authorization: Bearer` for the first three, `Project-Access-Token` for the fourth — and `kind` is declared in configuration and validated at startup, never inferred.<br><br>**Rejected:** one `RAILWAY_TOKEN` variable with the header guessed from the token's shape. The shapes are not documented, and a wrong guess yields `"Not Authorized"` with nothing in the response that says "wrong header". **Rejected:** try `Bearer`, fall back to `Project-Access-Token` on failure. Doubles the cost of every genuine auth failure and disguises a revoked token as a header problem. Source: `_research/2026-09-14-railway-public-api.md`, `…-graphql-surface.md` §3, §7. |
| D-API-3 | proposed | Errors are classified from the response body first and the HTTP status second, into a closed `RailwayError` union (`not-authorized`, `validation`, `rate-limited`, `network`, `unknown`). The string match on `"Not Authorized"` lives in exactly one named place with its research citation. `traceId` is kept on every error. No Railway response body is ever forwarded to the browser; the console's error shape is its own.<br><br>**Rejected:** branching on the HTTP status. The observed auth failure is a `200`; `response.ok` would call it success. **Rejected:** forwarding Railway's `errors[]` to the client. It leaks schema and message strings into a UI, and binds the UI to a format Railway does not promise. Resolves nothing on its own; carries `Q-SEC-3`. Source: `_research/2026-09-14-railway-graphql-surface.md` §3.<br><br>**Extended 2026-09-14 by experiment:** a plain input-validation failure (`numReplicas: 0`) also returns HTTP 200 with `extensions.code: INTERNAL_SERVER_ERROR` and a useful message, `"Error in numReplicas - Invalid input"`. So the code separates neither auth nor validation, and `kind: 'unknown'` must carry Railway's `message` through to the UI rather than swallow it. |
| D-API-4 | proposed | Whether the container is up is derived from `latestDeployment.status`, `latestDeployment.instances[].status` and `deploymentStopped` together, by a pure, total function that returns an explicit `unknown` for any combination it does not recognise. `deployment.status` alone is never read as the answer.<br><br>**Rejected:** `status === 'SUCCESS'` means up. `DeploymentStatus` has no `STOPPED`; a stopped deployment keeps `SUCCESS` and reports the stop through its instances, so this reading shows a stopped container as running — the exact lie `D-UI-1` exists to prevent. **Rejected:** collapsing to a boolean. It loses `starting`, `stopping`, `failed`, `sleeping`, which are the states the console is for. Source: `_research/2026-09-14-railway-domain-model.md`.<br><br>**Confirmed 2026-09-14 by experiment.** After a real `deploymentStop`: `status=SUCCESS`, `deploymentStopped=true`, `instances=[EXITED]` — stable. Rows 8, 9 and 12 move from `[to-verify]` to `[observed]`; `STOPPED` was never seen, only `EXITED`. **And a trap was found:** a deployment that has not started yet reads `deploymentStopped=true` with `instances=[]` while `status=DEPLOYING`. The table survives only because it matches on `status` (rows 4–7) *before* it looks at `deploymentStopped` (row 8). That ordering is now load-bearing and is verified explicitly by `V-33`. |
| D-API-5 | proposed — **owner decides** (`Q-API-2`) | **Revised 2026-09-14 after the experiment. Recommended pair: down = `deploymentStop(latestDeployment.id)`, up = `deploymentRestart(id)` when a stopped deployment exists, else `serviceInstanceDeployV2`.** Verified live: restart revives a *stopped* deployment in ~8 s keeping the same deployment id, though the published gloss says restart is for *running* deployments. That is the only pair where the console may honestly say the same container came back; `serviceInstanceDeployV2` costs a new deployment and ~16 s. Candidate (b) `numReplicas: 0` is **dead** — the API rejects `0` outright. Detail in `_research/2026-09-14-experiment-stop-and-start.md`.<br><br>**Superseded reasoning below, kept because it is what was believed before the experiment.** The four candidates for "down" differ in what survives and are laid out in `_research/2026-09-14-railway-operations-and-cost.md` §2. The recommended pair is **up = `serviceInstanceDeployV2(serviceId, environmentId)`**, **down = `deploymentStop(latestDeployment.id)`**, on the grounds that it is the narrowest verb that stops the container while keeping the service, its configuration and its deployment history — and that `deployV2` returns the id the console then subscribes to. It holds only if the `Q-API-6` experiment shows a stopped deployment reads as `down` through `D-API-4`.<br><br>**Alternatives, for the owner to weigh — not rejected by an agent:** (a) `deploymentRemove` — the verb behind the dashboard's *Remove*; also stops the container, but moves the deployment to history and *"Removed deployments are not recoverable through standard means"*; closest to what a Railway user would expect "down" to do. (b) `serviceInstanceUpdate(numReplicas: 0 \| 1)` — keeps everything and is applied without a redeploy, but `0` is neither allowed nor forbidden in the docs (`Q-API-5`) and it is a configuration edit standing in for a lifecycle verb. (c) `serviceCreate` / `serviceDelete` — the most literal "spin up a container" (a new one each time), but *"will delete the service and all its deployments"*, so nothing survives and the UI can never show history. (d) **`deploymentStop` ↔ `deploymentRestart`** — the pair a Railway employee recommended on the support forum for "temporarily disable via the API" (`_research/2026-09-14-railway-customers-and-users.md` §4, secondary); keeps the same deployment id, so "the same container came back" becomes sayable; needs `serviceInstanceDeployV2` for the first-ever up, and the forum thread hints the dashboard status may lag. If the owner prefers it, the recommendation above changes only in the body of `Up.graphql`: *restart if a stopped deployment exists, else deploy*.<br><br>**Rejected outright:** `deploymentRedeploy` as "up" — needs a previous deployment, so the first ever up has nothing to act on; the V1 `serviceInstanceDeploy` and `environmentTriggersDeploy` — return `Boolean`, forcing a follow-up read to learn which deployment to watch. |
| D-API-6 | proposed | The console addresses exactly one `(projectId, environmentId, serviceId)`, supplied by configuration. There is no route, query or screen for choosing a project, environment or service.<br><br>**Rejected:** a picker. It needs an account- or workspace-scoped token to list anything, turns a two-button console into a dashboard clone, and answers a question the brief did not ask. **Rejected:** deriving the triple from a project token via `query { projectToken { projectId environmentId } }`. Works for one token type only, and the service id still has to come from configuration. The "how would you extend it" answer is the picker; that is why it is recorded here as rejected rather than omitted. Source: `_research/2026-09-14-railway-domain-model.md`, last section. |

## Deployment of the console — `D-OPS-N`

| ID | Status | Statement |
|---|---|---|
| D-OPS-1 | proposed | **The console runs as one service in its own Railway project; the container it controls is a separate service in a separate project**, deployed from a small public image with serverless off, addressed by a project token scoped to that project's environment. Usage limits are set on the account before either is deployed.<br><br>**Rejected:** console and target in the same project. One dashboard and one token, but a misconfigured `RAILWAY_SERVICE_ID` would let the console stop itself, and a reviewer opening the project sees two services and has to work out which is the demo. **Rejected:** target service created by the console at first run (`serviceCreate`) — only needed if the owner picks candidate (c) in `D-API-5`; otherwise it adds a mutation and a permission the console does not need. **Rejected:** deploying the console anywhere but Railway — R-5 says Railway. Resolves `Q-OPS-1`. |
| D-OPS-2 | proposed — **owner signs** | **The repository is a pnpm workspace driven by Turborepo: one deployable, `apps/console`, and three internal packages — `@repo/contracts`, `@repo/container-core`, `@repo/railway-client` — with one permitted dependency direction, `contracts ← container-core ← railway-client ← console`.** `container-core` owns a `ContainerProvider` port; `railway-client` implements it. A package may import only what its `package.json` declares (pnpm's isolated `node_modules` enforces this) and only through the other package's `exports` map. Boundaries become resolution errors instead of review comments.<br><br>**Rejected:** one application with folders — the layout PR #4 merged. The three import rules of `changes/railway-container-control/design.md` §2 live in prose and two grep checks, and the code already violates the spirit of one: `src/railway/readContainer.ts` imports from `src/container/state.ts` and `state.ts` imports from `src/railway/types.ts`, a cycle nothing catches (`[observed]` 2026-09-14). **Rejected:** six packages — the three above plus `ui`, `typescript-config`, `eslint-config`. `ui` has no second consumer (the screen is one button, one headline, two lines); the base tsconfig is one root file; there is no linter to configure. Each is **set aside, not refused**: `ui` when a second screen exists, `eslint-config` when a linter is added (a separate change), `typescript-config` never, unless a package needs a different base. **Rejected:** separate repositories — one deploy, one PR history, one reviewer reading one tree. **Rejected:** `railway-client` independent of `container-core`, mapping to `ContainerView` in the app — puts the one mapping that must be right into the package with the fewest tests. Source: `changes/monorepo-workspace/design.md`. |
| D-OPS-3 | proposed — **owner signs** | **Internal packages are consumed Just-in-Time: each `exports` map points at `src/index.ts`, there is no `dist/`, Next.js transpiles the three packages via `transpilePackages`, and vitest runs them from source.** Only `apps/console` has a `build`; `railway-client` has a `check` (the operations gate) that the console's build depends on.<br><br>**Rejected:** compiled packages — `tsc` to `dist/` with declarations, the owner's original suggestion and the Turborepo docs' second strategy. Gains a Turborepo build cache per package and proof that each package compiles alone; costs a build step, a `tsconfig.build.json` each, `dist/` in the tree during `dev`, and a watch process per package. Three packages under a thousand lines have nothing to cache (`[observed]` in the Turborepo docs, 2026-09-14: *"Turborepo cannot cache a build for a Just-in-Time Package"* — and there is nothing worth caching), and pnpm already proves isolation. **Becomes the choice** when a consumer that is not a bundler appears — a CLI, a worker — or when build time is measurable. **Rejected:** publishable packages — nothing here is published. Source: `turborepo.dev/docs/core-concepts/internal-packages`, read 2026-09-14. |

## Tokens and secrets — `D-SEC-N`

| ID | Status | Statement |
|---|---|---|
| D-SEC-1 | proposed | The Railway API token is never exposed to the browser. Calls to `backboard.railway.com` are made from a server the console owns, and the client talks only to that server.<br><br>**Rejected:** calling the GraphQL endpoint directly from the browser with the token in an environment variable. It is fewer moving parts and it is what the brief's wording could be read to permit, but a deployed public demo would hand a working credential to anyone who opened devtools. **Rejected:** asking the reviewer to paste their own token into the UI — safer, but it puts a credential prompt in front of someone evaluating the work, which is a worse first thirty seconds. Resolves `Q-SEC-1`. |

| D-API-7 | proposed | **State is refreshed by bounded polling, not by a subscription.** One server-side poller reads `serviceInstance{ latestDeployment{…} }` on a schedule — every **30 s while idle**, every **2 s while a transition is in flight** (until a terminal phase or 90 s) — derives `ContainerState`, and pushes it to every browser over SSE. One poller serves all viewers; the browser still holds no state and still makes no Railway request. Budget against the observed 1 000/hour: 120 idle + ~45 per press.<br><br>**Rejected:** `subscription deployment(id)`, which `D-API-1` chose. It is refused outright for a project token, and even for an account token it does not fire when only the instances change — which is precisely what `deploymentStop` does. Choosing it would mean either abandoning least privilege (`D-API-2` prefers a project token) or missing the down transition, or both. **Rejected:** subscription for status changes plus polling for the rest. It is strictly more machinery than polling alone, for one saved request every 30 s, and it needs an account token in the console anyway. **Rejected:** polling only while a transition is in flight, never at idle. Cheapest, but the console would not notice a container stopped from the Railway dashboard until someone pressed something — `Q-UI-2` says it must. **Kept as an extension:** the subscription is a real capability and belongs in the "how would you extend it" answer, together with the reason it was not used. Supersedes `D-API-1`. Source: `_research/2026-09-14-experiment-stop-and-start.md`. |

## Console — `D-UI-N`

| ID | Status | Statement |
|---|---|---|
| D-UI-1 | proposed | The console shows the state the API actually reports, including the intermediate one, and never an optimistic guess about whether a container is up.<br><br>**Rejected:** flipping the toggle immediately and reconciling later. It reads as faster and it is how most consoles are built, but this product's whole subject is whether infrastructure is really running — a UI that lies for two seconds about that is lying about the only thing it exists to say. Depends on `Q-API-3` and `Q-UI-1` for how state is obtained — both since resolved by `D-API-1`. |
| D-UI-2 | proposed | **Stack: Next.js (App Router) + TypeScript, run as one Node process (`next start`), deployed as one Railway service.** Route handlers carry the four-route HTTP boundary from `D-API-6`; the same process holds the Railway socket (`D-API-1`) and serves SSE. No serverless/edge runtime — the long-lived socket and the SSE stream need a process that stays up.<br><br>**Why this and not something else, given the repository:** there is no code yet; the only signal is `.gitignore`, which already lists `.next/` and `.turbo/`, i.e. the owner anticipated Next. Railway builds Next.js without configuration. One deployable keeps the `OPS` change to one service and one set of variables. **Rejected:** Vite + React with a separate Hono/Express server — the same result with two build targets and a static-serving shim; nothing gained for a one-screen app. **Rejected:** SvelteKit / Remix — equally capable, but not what the repository hints at, and a reviewer's 30 minutes are better spent on the decisions than on an unfamiliar framework. **Rejected:** server-rendered HTML + htmx — satisfies R-4 literally, but the interesting part of this app *is* client state (`D-UI-3`), and htmx would hide it in fragments. |
| D-UI-3 | proposed | **The UI is a rendering of `ContainerState`, and nothing else.** One screen; one primary control whose label follows the phase (`Start` when `down`, `Stop` when `up`, disabled with the phase name while `starting` / `stopping`); the current phase and, while starting, the deployment step; the last error, if any, with its `traceId`. A press while a transition is in flight is a no-op in the browser **and** is refused by the server with `409 { error: "transition-in-flight" }`, because the mutations are not idempotent and a second tab bypasses a disabled button. On page load the first paint comes from `GET /api/container/state`, then the SSE stream takes over; nothing about state is stored in the browser, so a refresh mid-transition simply shows the transition. A change the console did not initiate (dashboard, sleep, crash) arrives over the same stream and is shown the same way — that is the answer to `Q-UI-2`.<br><br>**Rejected:** optimistic UI (see `D-UI-1`). **Rejected:** client-only guarding of double presses — the guard has to live where the mutation is issued. **Rejected:** queueing a press to run after the current transition — turns two clicks into a surprise a minute later. **Rejected:** persisting "I pressed Start at 12:03" in `localStorage` to survive refresh — the server already knows; the browser remembering is a second source of truth. Resolves `Q-UI-2`. |
| D-UI-4 | proposed | **The primary user is a developer managing a test environment** — someone who needs to start a specific version, check it, and stop it, and whose pains are picking the wrong environment and not knowing whether the operation finished (`_research/2026-09-14-user-hypotheses-and-cjm.md` §1). One scenario, one screen; the other three users are served only where it costs nothing.<br><br>**Alternatives, set aside for the MVP rather than rejected:** the *prototype developer* — needs "ready", not "running", which is Railway's healthcheck and is shown when configured, but the rest of their pain (not understanding infrastructure) asks for explanation the console does not attempt; the *QA engineer or designer* — needs names, not IDs, and no logs, which `Q-UI-4` partly absorbs, but "was handed a link" implies a share/permission story the console does not have; the *incident engineer* — needs diagnosis and permitted actions, i.e. logs, restart, rollback, roles — every one of them an extension in `design.md` §12, none in the MVP. **Rejected:** designing for all four at once — four interfaces before one is validated. Hypothesis until `Q-UI-3` (3–5 interviews in the chosen segment) is done; supported so far only by the support-forum evidence that this user exists and asks exactly the stage-6 question. |
