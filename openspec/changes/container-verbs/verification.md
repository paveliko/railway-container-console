**Amended by `vite-console`, recorded 2026-09-15.** `V-CV-5` … `V-CV-7` and
`V-CV-9` were written against the `createActions` shape of design §1/§2, which
was not built (design §5). They are reworded here — same ids, same claims where
the claim survives — to name where the behaviour actually lives. Each line ends

- V-CV-1 `unit` — With a transcript whose read returns the observed post-stop view (`SUCCESS` / `deploymentStopped: true` / `[EXITED]`), `up()` issues `RestartDeployment` exactly once, never `DeployServiceInstance`, and returns that deployment's id. *Covered:* `packages/railway-client/src/verbs.test.ts`, "revives a stopped deployment and keeps its id".
- V-CV-2 `unit` — With the read returning `{ hasEverDeployed: false, latestDeployment: null }`, `up()` issues `DeployServiceInstance` exactly once and never `RestartDeployment`. *Covered:* `verbs.test.ts`, "deploys a new instance when there is nothing to revive".
- V-CV-3 `unit` — With the read returning the `REMOVED` view, `up()` deploys — a removed deployment is not restarted. **No run.** `verbs.test.ts` carries `STOPPED`, `RUNNING` and `NEVER` fixtures only; the nearest case, "does not try to revive a deployment that is merely running", is `RUNNING`, a different branch. `T-CV-3` is open on this.
- V-CV-4 `unit` — `down()` issues `StopDeployment` against `latestDeployment.id` exactly once; with no deployment it rejects with `kind: 'no-deployment'` and issues nothing. *Covered:* `verbs.test.ts`, "stops the latest deployment by id" and "rejects with no-deployment when there is nothing to stop".
- V-CV-5 `unit` — **Reworded.** The guard is the poller's claim, not a flag on an actions object: a `POST /api/container/up` that reaches Railway leaves `poller.operation()` reading `{ transition: 'up', target: <the deployment the press is aimed at> }`, and the `202` carries that same id. `V-19` covers the clearing. *Covered:* `apps/console/src/server/routes.test.ts`, "a start answers 202 with the deployment it is waiting for".
- V-CV-6 `unit` — **Reworded.** While a transition is claimed, a second press is refused before any Railway request: two simultaneous presses yield `202` and `409 { error: 'transition-in-flight' }`, and the fake Railway records exactly one mutation and no read for the refused one (`V-18`, provider half). *Covered:* `routes.test.ts`, "two simultaneous presses issue one mutation; the other gets 409".
- V-CV-7 `unit` — **Reworded, and reconciled with `V-VC-9`.** The mutation is issued exactly once and never retried (`V-12`). What happens to the guard depends on what the failure proves: a **definite** refusal — `not-authorized`, `rate-limited`, a validation rejection — frees it at once, because the mutation demonstrably did not take effect. An **ambiguous** one — `network` — holds it, because the request may have reached Railway and a second press would double-fire. An ambiguous hold ends at whichever comes first: a confirmed outcome, in which case the operation resolves normally and may resolve as `succeeded`, or the deadline, which is the only path that reports `indeterminate`. *Covered:* `routes.test.ts`, "a definite refusal frees the guard" and "an ambiguous failure keeps the guard, so a second press cannot double-fire"; `packages/container-core/src/poller.test.ts`, cases 9, 9b and 9c; `verbs.test.ts`, "does not retry when the mutation rejects — V-12".
- V-CV-8 `build` — The mutation documents validate against the excerpt (`V-39`); a bogus field in one of them fails `pnpm turbo run check`. *Covered:* `railway-client#check` (`scripts/check-operations.ts`), which `console#build` depends on.
