# Verification: `console-server`

Prefix `V-CS-N`. Parent criteria cited by their `V-N`.

Each line ends with the run that covers it. First recorded 2026-09-15 against
the tree `vite-console` (PR #8) left, which verified its own `V-VC-N` and left
four criteria here unrun. Three of them — `V-CS-2`, `V-CS-5`, `V-CS-8`, and the
trailing clause of `V-CS-6` — were closed later the same day. `V-CS-9` is
`live` and still has none.

- V-CS-1 `build` — `pnpm turbo run build` succeeds with no `RAILWAY_*` variable set; **Amended by `vite-console`:** there is no framework to ask for a runtime. The equivalent guarantee is that `vite build` succeeds with no `RAILWAY_*` variable set — the build never imports the server — and that `start` runs one long-lived process. *Covered:* `pnpm build` runs `vite build` with no `RAILWAY_*` set, in `pnpm verify`; `apps/console/package.json` `start` is one long-lived `tsx src/server/main.ts`.
- V-CS-2 `unit` — `toConsoleError` maps a `ConfigError` raised by a missing `RAILWAY_TOKEN_KIND` to `500` with the body `{ error: 'console-misconfigured' }`; the body carries no variable name and no other prose, the variable is named in the server log, and no Railway request is made (fake `fetch` records zero calls). *(Reworded 2026-09-15 by `D-OPS-6`. It previously asserted that the first `GET /api/container/state` answers this, which `V-55` makes impossible — the process exits before it listens — and it claimed a `message` in the body that `consoleErrorSchema` has no field for.)* *Covered:* `apps/console/src/server/errors.test.ts`, "a misconfigured console — V-CS-2" — three cases: the mapping to `500 { error: 'console-misconfigured' }`; the body carrying the code and nothing else, asserted both as a key list and as the absence of `RAILWAY_TOKEN_KIND` from the serialised body, while the same variable *is* asserted present in the `console.error` an operator reads; and a stubbed `fetch` recording zero calls. The file did not exist before — `config.test.ts` covers `configFromEnv` throwing, which is a different assertion.
- V-CS-3 `unit` — Two `EventSource` clients and a third that reconnects each receive the current state as their first event; the fake `fetch` records the same number of reads as with zero clients (`V-26`, `V-26a`). *Covered:* `apps/console/src/server/sse.test.ts`, "opens with the current state and the current operation, costing no read" and "a reconnecting browser is told the press is still running"; `packages/container-core/src/poller.test.ts`, "the read count does not depend on how many clients are listening".
- V-CS-4 `unit` — A `: ping` comment is written at least once per 20 s of fake time on an open stream; closing the response unsubscribes (listener count returns to its previous value). *Covered:* `sse.test.ts`, "pings inside 20 s so a proxy keeps the socket — V-CS-4" and "a disconnect unsubscribes, and stops costing anything".
- V-CS-5 `unit` — Driving Start → starting → up → second press → Stop → down → `GET /state` against the fake Railway produces exactly the sequence of `ContainerState` phases the experiment recorded, and the second press is a `409` with no fake-Railway call (`V-17`, `V-18`). *Covered:* `apps/console/src/server/routes.test.ts`, "start → starting → up → stop → down, exactly as the experiment recorded" — one test driving the whole sequence over a real socket against `test/fake-railway.ts`, recording the poller's emissions as `['down/stopped', 'starting', 'up', 'down/stopped']`. The frames advance by hand (`setFrame` plus `pollOnce`) because the poller's loop is never started in this harness, so the recording is the transition list and not a sample of a timer. The second press sits inside the same test at the point the criterion puts it, answering `409` with the fake recording one `RestartDeployment` and no read; the pre-existing "two simultaneous presses issue one mutation; the other gets 409" covers the same-tick race. The `starting` frame — `SUCCESS` with a `CREATED` instance, since a restart never rebuilds — was added to the fake for this.
- V-CS-6 `unit` — Each scripted failure — not-authorized, `429` with `Retry-After: 30`, `429` without, the `numReplicas` validation body, a thrown `fetch` — yields the status and `ConsoleError` of parent §9, and the state served by `GET /state` afterwards is the last known one (`V-13`, `V-14`, `V-25`). *Covered:* `routes.test.ts`, "the error contract — Q-UI-7" — the parametrised failure → status/code table, "mirrors Retry-After when Railway sent one, and omits it when it did not", and "never forwards Railway prose, only the trace id"; and, for the trailing clause, "GET /state afterwards still serves the last known one" — after a `502`, the route answers with the state read before the failed press, and the fake's read count does not move, so it is the last known state rather than a fresh one that happens to agree.
- V-CS-7 `unit` — With `CONSOLE_PASSPHRASE=x`: `POST /up` without the cookie → `401`; `POST /api/session` with the wrong passphrase → `401`; with the right one → `204` + `Set-Cookie` (HttpOnly, SameSite=Strict); then `POST /up` → not `401`. Without the variable, `POST /up` needs no cookie (`V-20`). *Covered:* `routes.test.ts`, "the passphrase gate — V-20, V-CS-7" — all four cases, plus the cross-origin refusal.
- V-CS-8 `unit` — Every `ConsoleError` body the routes can produce parses with `consoleErrorSchema` from `@repo/contracts` (snapshot over all kinds, `V-13`). *Covered:* `errors.test.ts`, "every error body parses with consoleErrorSchema — V-CS-8" — every error the server can raise, each body parsed with `consoleErrorSchema` and its code asserted, the exact field sets checked for the two bodies that carry more than a code (because the object schema is not strict, so `safeParse` alone would accept a stray key), and — the clause that makes it a snapshot over *all* kinds rather than a sample — the set of codes produced asserted **equal** to `consoleErrorCodeSchema.options`. A thirteenth code added to the enum without a mapping fails that assertion; proved by dropping one mapping and watching it fail, then restoring it. The one body the routes write *without* going through `toConsoleError` — the `401` the session route answers a wrong passphrase with — is parsed with the schema over the wire in `routes.test.ts`, "exchanges the right passphrase for a hardened cookie, and accepts it".
- V-CS-9 `live` — `V-16`: a headless browser loading the running console makes requests to its own origin only. **No run.** `live`; no headless-browser test exists. `routes.test.ts` "refuses a cross-origin press" is the server-side half, not the browser-side claim. `T-CS-5` is open on this, and it is the one criterion in this change that needs something the repository does not have — a browser dependency, or one logged manual run. The owner decides which; see `changes/railway-container-control/tasks.md`.
